# 2.6 Local document parsing: requirements

Roadmap item: **2.6** (Phase 2). Branch: `feat/2.6-document-parsing`.

## Goal

Read uploaded documents locally and privately, with no Azure service: files are parsed in memory and never stored (principle 3 in `mission.md`).

## Scope

In scope:
- Domain:
  - `ParsedDocument`
  - `DocumentType.guess(filename)`, the rule the old upload router had inline
- Application:
  - the `DocumentParser` port and its errors (`Unsupported`, `Unreadable`)
  - the `ParseDocument` use case (10 MB limit, no text found)
- Infrastructure: `LocalDocumentParser` (pypdf, python-docx, and UTF-8 / CP1252 text).
- API: `POST /api/documents/parse` returns `{title, type, text, pages}`. Errors map to 413, 415 and 422 with messages the user can act on.
- Fixtures, generated by a committed script:
  - a 2-page PDF, a .docx with a table, and a .txt
  - a corrupt PDF, a corrupt .docx, an encrypted PDF, and a PDF with no text

Out of scope:
- Removing the Cosmos, Blob and Document Intelligence upload pipeline (2.7).
- OCR for scans (not planned; the message suggests a copy with selectable text).
- The frontend upload UI (3.3 splits the documents feature).

## Decisions

1. **Formats:** PDF, .docx, .txt and .md. Legacy `.doc` is binary and needs extra tooling, so it gets a clear 415.
2. **The parser adapter is synchronous.** pypdf and python-docx are CPU-bound and fast for 10 MB files. The route still reads the upload asynchronously, and at most 10 MB + 1 bytes.
3. **The fixtures are generated, not hand-picked.** The PDF is built byte by byte with a correct xref table, so pypdf reads it without warnings. The .docx has a fixed creation date, so regenerating it gives the same file.
4. **"Not stored" is tested.** The parser runs in an empty working directory, and the test checks that nothing was written.
